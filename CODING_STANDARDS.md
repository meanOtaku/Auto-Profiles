# Coding Standards

## 1. Language and Version

Use Python 3.11 as the minimum language version. Python 3.12 may be supported through the CI matrix, but code must remain compatible with Python 3.11 until an explicit migration changes the minimum version.

## 2. Style and Tooling

Use:

- Ruff for formatting and linting
- mypy as the type checker
- pytest for tests

Dependencies must be reproducibly locked using the package-management workflow selected in `pyproject.toml`. Model artifacts are dependencies and must be pinned by version and checksum.

The repository configuration is the source of truth.

## 3. Type Safety

- Type all public functions and methods.
- Type domain models and protocol interfaces.
- Avoid `Any` unless interoperability requires it.
- Document justified `type: ignore` comments.
- Prefer `Protocol` for injectable interfaces.

Example:

```python
from typing import Protocol

class FrameSource(Protocol):
    def open(self) -> None: ...
    def read(self) -> Frame: ...
    def close(self) -> None: ...
```

## 4. Module Design

- Keep modules focused on one responsibility.
- Avoid circular dependencies.
- Domain code must not import UI code.
- Vision code must not depend directly on database implementations.
- OS-specific settings code must remain behind adapters.
- APIs should call application services rather than repositories directly.

## 5. Naming

Use descriptive names.

```text
profile_id
recognition_threshold
candidate_expiry_seconds
active_user_switch_margin
```

Avoid unexplained abbreviations.

## 6. Functions and Methods

- Prefer small functions with explicit inputs and outputs.
- Avoid hidden global state.
- Separate pure decision logic from I/O.
- Use early returns for invalid or terminal conditions.
- Do not mix model inference, persistence, and settings application in one function.

## 7. Data Models

Use dataclasses or Pydantic models according to context:

- Dataclasses for internal immutable domain values
- Pydantic for configuration and API schemas
- ORM models only in the persistence layer

Do not pass ORM objects through the entire application.

## 8. Immutability

Prefer immutable event and result objects.

```python
@dataclass(frozen=True)
class QualityResult:
    accepted: bool
    score: float
    reasons: tuple[str, ...]
```

## 9. Error Handling

- Raise specific exceptions.
- Do not catch `Exception` without re-raising or logging with context.
- Never suppress database-integrity errors silently.
- Convert internal exceptions to API errors at the API boundary.
- Include correlation identifiers for cross-component operations.

## 10. Logging

Use structured logging.

Include fields such as:

- event_type
- camera_id
- track_id
- profile_id
- candidate_id
- correlation_id
- duration_ms

Do not log:

- Raw embeddings
- Full face images
- Secrets
- Passwords or tokens

## 11. Configuration

- No magic thresholds.
- All recognition, quality, enrollment, tracking, and active-user values must be configurable.
- Validate configuration at startup.
- Use safe defaults for development.
- Fail clearly for invalid production configuration.

## 12. Time

- Use timezone-aware UTC timestamps internally.
- Convert time for display only at the UI boundary.
- Inject clocks into time-sensitive domain services when practical for testing.

## 13. Identifiers

Use UUIDs for profiles, candidates, events, and persistent embeddings. Temporary tracker IDs may be strings or integers scoped to a runtime session.

## 14. Numeric Data

- Normalize face embeddings before storage and comparison.
- Use a consistent numeric dtype.
- Record model name and model version with every embedding.
- Do not compare embeddings generated by incompatible models without an explicit migration strategy.

## 15. Concurrency

- Use bounded queues.
- Avoid shared mutable state.
- Guard profile promotion and merge operations with transactions.
- Make shutdown cooperative and deterministic.
- Do not allow stale frames to accumulate indefinitely.
- Do not perform model inference or blocking camera/OS calls directly on the API event loop.
- Define queue capacity, overflow policy, cancellation behavior, and shutdown ownership.
- Durable domain events must not be dropped when transient frame telemetry is discarded.

## 16. File and Path Handling

Use `pathlib.Path`. Keep runtime data outside source directories. Never assume the current working directory is the repository root.

## 17. API Design

- Validate all inputs.
- Use stable response schemas.
- Return machine-readable error codes.
- Use pagination for potentially large collections.
- Use idempotent semantics where appropriate.
- Protect destructive operations.
- Version public routes under `/api/v1`.
- Require authentication and authorization for non-loopback deployments.
- Fail startup when exposed beyond loopback without production security configuration.
- Define idempotency and optimistic concurrency for retryable state-changing operations.
- Apply request-size limits, rate limits, and sanitized error responses.

## 18. Security, Privacy, and Supply Chain

- Never persist permanent biometric data without the configured encryption-at-rest protection.
- Never include image arrays or embedding values in `repr`, exceptions, traces, metrics, or logs.
- Keep encryption keys separate from encrypted data.
- Verify model and fixture checksums before use.
- Record third-party dependency and model licenses.
- Run dependency vulnerability and secret scans in CI.
- Treat exports, temporary files, database sidecars, and backups as sensitive data.
- Domain modules must not read secrets or environment variables directly; configuration boundaries provide validated values.

## 19. Documentation

Every public module, class, and non-obvious function should explain intent, not restate code. Complex thresholds and policy decisions require rationale.

## 20. Comments

Use comments for:

- Safety constraints
- Performance trade-offs
- Non-obvious model behavior
- External-system limitations

Do not leave commented-out code.

## 21. Prohibited Patterns

Do not:

- Create a permanent profile from one frame
- Apply OS settings directly from recognition code
- Place business logic in API routes or UI components
- Hardcode file paths or thresholds
- Store embeddings in logs
- Use real cameras in unit tests
- Add silent fallbacks that change recognition behavior
- Claim state transitions without emitting or logging them
- Enable automatic candidate promotion without verified consent, liveness, retention, and security gates
- Expose administrative APIs beyond loopback without authentication and authorization
- Load unverified model artifacts
