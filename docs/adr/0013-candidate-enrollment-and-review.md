# ADR 0013: Candidate Enrollment and Owner-Reviewed Promotion

- Status: Accepted
- Date: 2026-08-01
- Decision milestone: M8

## Context

M8 must create temporary candidates, collect consistent observations, prevent duplicates against both active profiles and other candidates, apply minimum spoof/replay checks, and promote only with explicit owner approval by default — atomically, auditably, and idempotently. HERMES rule 15 and this repository's own configuration validation must keep automatic promotion disabled until liveness (M14), retention, and API security (M12) exist. A prerequisite defect had to be fixed first: M6's repositories committed after every single write, which made it impossible to compose profile-creation, multi-embedding transfer, candidate-state transition, and audit-event recording into one atomic promotion transaction.

## Decision

**M6 correction.** `database/repository.py` write methods no longer call `connection.commit()` themselves; the caller now owns the commit/rollback boundary (`ProfileDatabase.commit()`/`.rollback()` were added). `merge()` and `import_profile()` remain self-committing because each is itself one atomic multi-statement unit. The M6 CLI `profile` commands were updated to commit explicitly. This is a compatibility-breaking change to M6's still-unverified, still-"drafted" repository API, made explicitly to unblock M8's atomicity requirement, and is recorded here and in the M8 report rather than silently folded into history.

**Schema.** Migration v2 (`database/schema.py`) adds `candidates`, `candidate_embeddings`, and a single-row `candidate_name_sequence` counter backing predictable `Unknown-000001`-style names. `candidate_embeddings.encrypted_vector` uses the same AES-256-GCM field encryption as `face_embeddings` — a temporary candidate is still biometric data. `recognition_events.candidate_id` remains a plain column without a foreign key: SQLite cannot add a `REFERENCES` constraint to an existing column without rebuilding the table, so retrofitting it is a documented, deferred follow-up, not a risky migration performed here.

**Lifecycle (`database/candidate_repository.py`).** `CandidateStatus` implements HERMES's state machine as `COLLECTING → {EXPIRED, REJECTED, READY_FOR_REVIEW} → PROMOTED`. `CREATED` is treated as momentary and not persisted as a separate row: a candidate becomes observable only once it has a sample. `reject()` and `expire()` both delete the candidate's `candidate_embeddings` rows immediately — an expired or rejected candidate's biometric data does not linger. `mark_promoted()` deletes the candidate-side embedding copies in the same transaction that copies them to the new profile, so a promoted person's biometric data is never stored twice.

**Qualification (`enrollment/qualification.py`, `enrollment/frontality.py`).** `evaluate_candidate_qualification()` is a pure function checking, all in one pass and reporting every failing reason: minimum sample count, minimum observation duration, minimum aggregate quality, at least one near-frontal sample (a dedicated, self-contained pose check, deliberately independent of M4's looser acceptance bounds), internal embedding consistency (rejects mixed-identity candidates via minimum pairwise similarity), a minimum temporal-variability check (rejects candidates whose samples are suspiciously near-identical, i.e. maximum pairwise similarity above a near-1.0 bound — a static/replayed input rather than naturally varying live capture), and duplicate checks against both active profiles and other in-flight candidates. This temporal-variability check is explicitly documented as the "minimum temporal spoof and replay checks" ROADMAP.md assigns to M8: a conservative statistical heuristic over the candidate's own samples, not a trained anti-spoof or liveness model. HERMES describes M14 as building on exactly these minimum checks.

**Orchestration (`enrollment/manager.py`).** `CandidateManager` maps each track ID to at most one in-flight candidate, so two simultaneously visible unknown people never share a candidate. It only ever creates a candidate for an M7 `UNKNOWN` observation (never `AMBIGUOUS` or `POSSIBLE_MATCH`), which keeps poorly observed *known* people from being immediately treated as new candidates. Once qualification passes, the candidate is automatically moved to `READY_FOR_REVIEW`; once a candidate is `READY_FOR_REVIEW` or `PROMOTED`, further observations for that track are dropped rather than raising, since owner review is now pending.

**Promotion (`enrollment/promotion.py`).** `CandidatePromoter.promote()` re-checks every candidate embedding against every active profile at promotion time (defending against a profile created after qualification but before promotion — verified in this session's smoke testing), rejects and deletes the candidate's samples if a duplicate is found, and otherwise performs profile creation, embedding transfer, candidate-state transition, and audit-event recording in one transaction. Calling `promote()` again on an already-`PROMOTED` candidate returns the existing profile without any further writes (idempotent retry safety).

**Configuration.** `EnrollmentConfig.automatic_promotion` is rejected unconditionally by a pydantic validator — not merely defaulted to false — because no production gate (liveness, consent, retention, API security) exists yet. This directly implements TESTING.md's required "automatic-promotion configuration is rejected when required production gates are missing" scenario, verified in this session.

CLI gains `candidate list|show|approve|reject`. The full HERMES REST surface (`/api/v1/candidates/...`) remains M12's job; this CLI is the interim, disabled-by-default review interface ROADMAP.md's "Candidate CLI/API review" deliverable calls for at this stage.

## Consequences

- Every M8 acceptance scenario was exercised in this session's smoke testing: a one-frame observation cannot reach `READY_FOR_REVIEW` (blocked by `minimum_samples`); two simultaneous unknown people get distinct candidates; a candidate that never qualifies expires with its embeddings deleted and no profile created; promotion is atomic, auditable (a `ProfileCreated` event links `profile_id` and `candidate_id`), and idempotent; a duplicate-profile race is caught and rejected at promotion time.
- Loading every active profile's and every other in-flight candidate's embeddings on each qualification check is the same documented O(n) performance limitation M7 already carries, deferred to M15.
- Printed-photo/replay resistance in M8 rests on (a) mandatory manual owner approval by default, so a human visually reviews before promotion, and (b) the minimum temporal-variability heuristic above. Neither is a trained anti-spoof model; this is an explicit, bounded gap M14 closes.
- Concurrent promotion attempts are not independently tested (TESTING.md scenario 10); SQLite's own transaction serialization and `busy_timeout` provide some protection, but dedicated concurrency testing remains a follow-up, consistent with M12 introducing the first concurrent workers.
