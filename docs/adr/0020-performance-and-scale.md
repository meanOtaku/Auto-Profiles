# ADR 0020: Performance and Scale — Adaptive Detection, Caching, Storage Limits, and Metrics

- Status: Accepted
- Date: 2026-08-01
- Decision milestone: M15

## Context

M15 must optimize detection frequency, tracking, batching, caching, and vector search, and deliver storage limits and a metrics dashboard/export, targeting at least 15 FPS, sub-two-second recognition confirmation, no profile creation from one-second appearances, and a low duplicate-profile rate — or a documented hardware-specific target when 15 FPS cannot be honestly claimed. No real camera hardware exists in this environment to benchmark, so real FPS/latency numbers are not fabricated here.

## Decision

**Recognition embedding caching (`recognition/embedding_cache.py`).** `ActiveProfileEmbeddingCache` amortizes M7's documented O(profiles × embeddings) per-call decrypt cost (ADR 0012/0013) across a configured `embedding_cache_refresh_seconds` instead of paying it on every `recognize()` call. `KnownPersonRecognizer` accepts it as an optional constructor parameter (default `None` preserves the exact prior always-fresh behavior for any caller that does not opt in), and `recognition/factory.create_recognizer()` always wires one in when recognition is enabled. `invalidate()` exists for a future caller (e.g., immediately after a promotion) to force a fresh read rather than waiting out the interval; wiring that invalidation call is a documented follow-up, not done in this milestone.

**Adaptive detection frequency and tracking between detections (`vision/tracking.py`, `api/worker.py`).** `GeometricFaceTracker` gained `predict_only()`, advancing every track's box by the same motion-prediction model `update()` already uses internally, without requiring new detections. `PipelineWorker` gained `detection_interval_frames` (default `1`, i.e. unchanged behavior): when greater than one, the detector is invoked only every Nth frame, and `predict_only()` keeps tracks alive on the skipped frames. Predicted geometry is deliberately never fed into quality/alignment/embedding/recognition — those stages only ever see a real detection — so this optimization cannot silently degrade recognition or enrollment accuracy; it only reduces detector invocation frequency and the per-track work gated behind it. Raising `detection_interval_frames` requires raising `tracking.max_missing_frames` proportionally or tracks will expire between detections; this is documented, not silently handled.

**Storage limits.** `ProfileRepository.add_embedding()` gained a `max_embeddings` parameter (default `50`, matching `EnrollmentConfig.maximum_samples_per_candidate`'s existing default so a normal candidate promotion is never silently truncated) that raises rather than allowing unbounded per-profile growth. `DatabaseConfig.maximum_embeddings_per_profile` (default `50`) is threaded through `CandidatePromoter` via `enrollment/factory.py`. `import_profile()` uses the method's default bound rather than a configurable one, a deliberate scope reduction: it already cannot exceed what was legitimately exported from a bounded profile in normal use, and a dedicated configurable import cap is a documented follow-up.

**Vector search / FAISS.** No FAISS (or equivalent) dependency was added. HERMES/ROADMAP explicitly frame this as "when justified" — every dataset in this repository's automated paths is tiny (single-digit to low-hundreds of profiles in any realistic test), where a brute-force cosine scan (`recognition/matcher.find_nearest_profiles()`, already O(n) linear) is faster in practice than the overhead of an approximate index, and adding a new native-compiled dependency (`faiss-cpu`) for an unjustified workload size would violate CONTRIBUTING.md §10's dependency-justification requirement. This is a considered non-decision: the embedding cache plus the existing linear scan are judged sufficient at the scale this project currently operates at, and FAISS remains a documented, ungated future option if profile counts grow to justify it.

**Metrics export (`api/routes.py`).** `GET /api/v1/metrics` (authenticated, like every other non-health route) returns a small JSON snapshot — worker state, frames processed/detected, detection-skip ratio, and active-profile/candidate counts — deliberately not a full Prometheus text-format endpoint or dashboard, which was judged out of scope for the remaining effort in this milestone. It contains no biometric payloads or per-person identifiers beyond aggregate counts, consistent with CODING_STANDARDS.md §10/§18.

**Honest performance targets.** No FPS or latency number is claimed as measured. This environment has no real camera and no benchmarking was performed against real hardware in this session. The "at least 15 FPS" and "recognition confirmation within two seconds" acceptance criteria remain explicitly unverified; HERMES's own fallback ("or a documented hardware-specific target") is exercised by recording that fact here rather than fabricating a number. "No profile creation from one-second appearances" was already structurally guaranteed by M8's `minimum_samples`/`minimum_observation_seconds` gates (verified in M8's own smoke testing) and is unaffected by this milestone. "Low duplicate-profile rate" likewise depends on M8's duplicate-detection thresholds, unevaluated on real data for the same reason as every prior milestone's threshold defaults.

## Consequences

- All changes are additive/optional-parameter and preserve exact prior behavior when unconfigured: `embedding_cache=None`, `detection_interval_frames=1`, and `max_embeddings=50` (a generous default, not a behavior-changing regression for existing tested flows) all reproduce pre-M15 behavior.
- Verified in this session: the embedding cache's TTL-refresh and manual-invalidate semantics (including a recognizer end-to-end call using the cache); `predict_only()`'s motion extrapolation and correct re-association with the same track once real detection resumes; the worker's adaptive scheduling invoking the detector exactly `frames / detection_interval_frames` times; the storage limit rejecting a profile's embedding count past its configured maximum; and the `/metrics` endpoint's authenticated JSON response.
- Real FPS/latency benchmarking against actual camera hardware, wiring `ActiveProfileEmbeddingCache.invalidate()` after promotions, a configurable import-time embedding cap, and any FAISS-backed index if profile counts eventually justify it all remain explicit, honestly recorded follow-ups — not claimed as done here.
