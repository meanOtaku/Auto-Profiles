# M12 Implementation Report — Headless Daemon and API

- Milestone: M12 — Headless Daemon and API
- Date: 2026-08-01
- Status: **Implementation drafted; verification deferred by owner**

## Scope delivered

- `api/app.py`: FastAPI app factory wiring M6–M11 into one process; lifespan starts/stops the worker and closes the database.
- `api/auth.py`, `api/rate_limit.py`: bearer-token auth (constant-time compare) and fixed-window rate limiting.
- `api/routes.py`: the full HERMES `/api/v1` surface (profiles, candidates, events, settings, system pause/resume, WebSocket live events).
- `api/worker.py`: `PipelineWorker`, a threaded detect→track→quality→align→embed→recognize→enroll→select-active-user→learn-preferences loop with pause/resume/health.
- `APIConfig`, disabled by default, with a fail-closed non-loopback validator.
- CLI `serve` command.
- Two real bugs found and fixed during this milestone's own smoke testing (see below).

## Explicit exclusions

M12 does not implement the bounded-queue multi-worker architecture ARCHITECTURE.md §5 describes (M15), a true pub/sub event bus (the WebSocket is poll-based), or a shared-store rate limiter for multi-instance deployment.

## Configuration

`api` is disabled by default. Enabling it beyond loopback without `auth_token` is rejected at config-load time.

## Commands executed

- `ruff format` and `ruff check .`: passed.
- `mypy src tests`: passed with no issues in 65 source files.
- `uv add fastapi==0.121.2 uvicorn==0.38.0 websockets==15.0.1`, `uv add --dev httpx==0.28.1`: resolved and installed successfully.
- Ad hoc, non-persisted interpreter smoke checks via FastAPI's `TestClient` (no real network port opened, no lingering process):
  - Health (no auth) succeeds; `/status` returns 401 without a token and 200 with the correct one.
  - Full profile lifecycle through the API: create (via repository) → GET → PATCH (with a stale-version PATCH correctly returning 409) → merge → export → import → `PUT` settings → soft delete, each producing the expected durable audit event (`ProfileUpdated`, `ProfileMerged`, `SettingsChanged`, `ProfileDeleted`).
  - Full candidate lifecycle through the API: seeded via `CandidateManager` → list → approve (idempotent: a repeated approve call returns the identical profile with no further writes) → a second candidate rejected and then deleted.
  - Rate limiting: a 3-per-minute limit correctly returned 429 on the 4th/5th rapid request; `/health` was correctly exempt.
  - WebSocket `/events/live`: connects and accepts with a correct token, disconnects with an incorrect one.
  - CLI `serve`: correctly refuses with exit code 3 when `api.enabled` is false, and the fail-closed non-loopback-without-token case correctly refuses at config load (exit code 2) before any app/server code runs.
- A real cross-thread SQLite bug was found and fixed: the M6 connection, created on one thread, crashed (`sqlite3.ProgrammingError`) when accessed from the ASGI lifespan/request thread. Fixed with `check_same_thread=False`, gated on verifying `sqlite3.threadsafety == 3` at open time. Re-verified after the fix (no crash across the full smoke-test suite above).
- A real API design defect was found and fixed: `DELETE /profiles/{id}` originally took `expected_version` as a JSON body, which `httpx.TestClient.delete()` (and many HTTP clients/browsers) do not support cleanly. Changed to a query parameter.
- Automated `pytest` and the full quality/packaging matrix were **not run**, per the owner's explicit request to defer tests for now.

## Verification status and limitations

No test counts, passing quality gates, or production-readiness claims are made. `face-profile serve` was never run as a live, long-lived process in this session (`create_app()` plus `TestClient` cover the same code paths without leaving a server listening, appropriate for a sandboxed session) — real end-to-end `uvicorn` serving, "service starts automatically after reboot" (a systemd/launchd/Windows-service installation concern), and real-camera worker operation are not claimed as verified. The WebSocket stream is poll-based (1-second interval), not push-based. No shared-store rate limiter exists for multi-instance deployment. `PipelineWorker`'s full pipeline wiring has not been exercised end-to-end with real detections (only its constituent M2–M11 stages were individually smoke-tested in their own milestones).
