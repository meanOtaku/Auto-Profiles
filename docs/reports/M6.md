# M6 Implementation Report — Persistent Profile Database

- Milestone: M6 — Persistent Profiles
- Date: 2026-08-01
- Status: **Implementation drafted; verification deferred by owner**

> **Amendment (2026-08-01, during M8):** `database/repository.py` write methods originally committed their own transaction after every call. This made them impossible to compose into a single atomic multi-write operation, which M8's candidate-promotion transaction required. The auto-commit behavior was removed; callers now own commit/rollback via `ProfileDatabase.commit()`/`.rollback()`, except `merge()` and `import_profile()`, which remain self-committing atomic units. See ADR 0011's addendum and ADR 0013/`docs/reports/M8.md` for the full correction. All M6 smoke-test scenarios were re-verified after the fix.

## Scope delivered

- SQL migration framework (`database/schema.py`) creating `profiles`, `face_embeddings`, `profile_settings`, and `recognition_events`, tracked in a `schema_version` table.
- AES-256-GCM field-level encryption of embedding vectors (`database/crypto.py`), using the newly added `cryptography` dependency, with per-embedding associated data binding ciphertext to its owning profile.
- `LocalFileKeyProvider` (`database/keys.py`): a 32-byte key in its own owner-only file, separate from the database, generated on first use and rejected if permissions loosen.
- Hardened connection lifecycle (`database/connection.py`): `0700` directory, `0600` database file, WAL mode, foreign keys on, permission verification on every open.
- `ProfileRepository`: create/get/list/update (optimistic concurrency via `optimistic_version`), `disable`, `soft_delete` + `purge_expired` (retention), atomic `merge` with correct AEAD re-keying, embedding add/list/get/remove, and encrypted `export_profile`/`import_profile`.
- `ProfileSettingsRepository` and append-only, sequence-numbered `RecognitionEventRepository`.
- `DatabaseConfig`, disabled by default, gating a `create_profile_database()` factory that follows the M1–M5 disabled-by-default pattern.
- CLI `profile create|list|show|delete|merge`, structured logging of profile lifecycle events, durable event recording on create/delete/merge.

## Explicit exclusions

M6 does **not** add `candidates`/`candidate_embeddings` schema (M8), the M7 recognition-decision state machine, real settings adapters (M9), active-user selection (M10), or a network API (M12). Representative face-image byte storage remains disabled; only embedding vectors are encrypted, matching ARCHITECTURE.md's biometric-data scope.

## New dependency

`cryptography==46.0.3` was added (via `uv add`, updating `pyproject.toml` and `uv.lock`) to provide AES-256-GCM. It is the de facto standard, actively maintained Python cryptography library (BSD/Apache-2.0 dual license); no standard-library AEAD cipher exists, and using OpenCV's DNN module (as M5 did to avoid an `onnxruntime` dependency) has no analogous applicability here.

## Configuration

`database` is disabled by default and bounds `path`, `key_path` (must differ from `path`), and `retention_days`.

## Commands executed

- `uv add cryptography==46.0.3`: resolved and installed successfully.
- `ruff format` and `ruff check .`: passed.
- `mypy src tests`: passed with no issues in 36 source files.
- Ad hoc, non-persisted interpreter smoke checks (not pytest, not committed as tests): profile creation and restart survival (reopening the database file in a fresh connection), multiple embeddings per profile with decrypt round-trip, optimistic-concurrency conflict rejection, settings upsert/read, durable event recording, atomic merge (including the AEAD re-keying fix, verified by decrypting every moved embedding post-merge), soft-delete + retention-based purge (confirmed not-yet-expired profiles survive and expired ones are removed), and encrypted export/import with a fresh UUID and successful embedding decryption. CLI `profile create`/`profile list` were exercised end-to-end against a temporary database file and correctly persisted across separate `main()` invocations.
- A real bug was found and fixed during this session's own smoke testing (not by an automated suite): embedding ciphertext associated data was bound to the profile ID at encryption time, so the initial `merge()` implementation's blind `UPDATE face_embeddings SET profile_id = ...` broke authenticated decryption for every moved embedding. `merge()` now decrypts under the source binding and re-encrypts under the target binding inside the same transaction; this was re-verified after the fix.
- Automated `pytest` and the full quality/packaging matrix were **not run**, per the owner's explicit request to defer tests for now.

## Verification status and limitations

No test counts, passing quality gates, or production-readiness claims are made. `purge_expired()` performs a normal SQL `DELETE`, not a disk-page secure-wipe. Backup/restore procedure (database file + separate key file together) is documented in the ADR but not automated or drilled. `recognition_events.sequence` assignment is not safe under concurrent writers (not introduced until M12). `LocalFileKeyProvider` is not HSM/KMS-backed; rotation is a manual, undocumented-in-tooling procedure. No migration downgrade path exists (none is needed yet: v1 is the initial schema), and only one schema version has ever been applied, so upgrade-from-every-supported-version testing (CONTRIBUTING §9) is not yet meaningful.
