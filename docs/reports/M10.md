# M10 Implementation Report — Active-User Selection

- Milestone: M10 — Active-User Manager
- Date: 2026-08-01
- Status: **Implementation drafted; verification deferred by owner**

## Scope delivered

- `presence/active_user.py`: `PresenceCandidate`, `ActiveUserState` (`NONE`/`CANDIDATE_ACTIVE`/`ACTIVE`/`LEAVING`), `ActiveUserDecision`, `ScoreWeights`, pure `compute_score()`, and stateful `ActiveUserSelector` implementing scoring, hysteresis (switch margin + stability duration), switch cooldown, and a leaving grace period.
- `presence/builder.py`: `build_presence_candidate()`, restricting eligibility to M7 `CONFIRMED_MATCH` tracks only.
- `ActiveUserConfig`, disabled by default, and `presence/factory.create_active_user_selector()`.

## Explicit exclusions

M10 does **not** apply settings to any adapter or learn/save preferences (M11); it only produces `ActiveUserDecision` values. It does not decide recognition identity (M7).

## Configuration

`active_user` is disabled by default and bounds score weights, duration/priority normalization scales, `switch_margin`, `stability_duration_seconds`, `switch_cooldown_seconds`, `min_visible_duration_seconds`, and `leaving_grace_seconds`.

## Commands executed

- `ruff format` and `ruff check .`: passed.
- `mypy src/face_profile`: passed with no issues in 45 source files.
- Ad hoc, non-persisted interpreter smoke checks (not pytest, not committed as tests), covering every TESTING.md §7 active-user scenario:
  1. One known user: `CANDIDATE_ACTIVE` while stability duration accrues, then `ACTIVE`.
  2. Two known users with different face sizes / a brief challenger: the brief challenger never accumulates enough consecutive stable time and the original active user is retained.
  3. Active user moves off-centre but remains the best candidate: stays active.
  4. Two known users with a sustained stronger challenger: switches only after both stability duration and cooldown are satisfied.
  5. Priority profile enters and wins on otherwise-equal geometry — this scenario is exactly the one that surfaced a real floating-point precision bug (see below).
  6. Cooldown prevents rapid switching: a second strong challenger immediately after a switch is correctly held off.
  7. Active user leaves (with unknown people explicitly excluded from eligibility): transitions through `LEAVING` for the configured grace period, then to `NONE`.
- A real bug was found and fixed during this session's own smoke testing: the switch-margin comparison `(challenger_score - active_score) < switch_margin` used strict floating-point comparison, so a challenger whose true score difference was exactly the configured margin lost by float-summation error (`0.09999999999999998 < 0.1`) and was silently never even considered as a pending challenger. Fixed with a small epsilon tolerance on the comparison, per TESTING.md §4. Re-verified after the fix.
- `build_presence_candidate()` was verified to produce a valid, range-correct candidate for a `CONFIRMED_MATCH` decision and to correctly return `None` for an `UNKNOWN` decision.
- Automated `pytest` and the full quality/packaging matrix were **not run**, per the owner's explicit request to defer tests for now.

## Verification status and limitations

No test counts, passing quality gates, or production-readiness claims are made. Score weight defaults are unevaluated starting points from ARCHITECTURE.md §10's suggested formula, not locally validated production values. `ActiveUserSelector` has not yet been exercised inside a real end-to-end pipeline (M3 tracker → M7 recognizer → M10 selector wired together over live or recorded frames); only unit-level scenarios with hand-constructed candidates and timestamps have been run. No CLI or daemon surface consumes `ActiveUserSelector` yet — that wiring is M12's headless-daemon job.
