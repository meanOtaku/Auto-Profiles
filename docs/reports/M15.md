# M15 Implementation Report — Performance and Scale

- Milestone: M15 — Performance and Scale
- Date: 2026-08-01
- Status: **Implementation drafted; verification deferred by owner**

## Scope delivered

- `recognition/embedding_cache.py`: `ActiveProfileEmbeddingCache`, a TTL-refreshed cache amortizing M7's documented per-call decrypt cost; wired into `KnownPersonRecognizer` (optional, backward-compatible) and `recognition/factory.py` (always constructed when recognition is enabled).
- `vision/tracking.py`: `GeometricFaceTracker.predict_only()` — motion-prediction-only track advancement without new detections, added to the `FaceTracker` protocol.
- `api/worker.py`: `detection_interval_frames` — adaptive detection frequency; skipped frames use `predict_only()` for continuity only, never feeding predicted geometry into quality/alignment/embedding/recognition.
- `database/repository.py`: `ProfileRepository.add_embedding()` gained a `max_embeddings` storage-limit parameter (default 50); wired through `CandidatePromoter` via a new `DatabaseConfig.maximum_embeddings_per_profile`.
- `api/routes.py`: `GET /api/v1/metrics`, an authenticated JSON snapshot (worker throughput, detection-skip ratio, active-profile/candidate counts).
- A considered decision **not** to add FAISS (documented in ADR 0020: unjustified at this project's current data scale, per HERMES's own "when justified" framing).

## Explicit exclusions

No real FPS/latency benchmarking (no camera hardware in this environment). No `ActiveProfileEmbeddingCache.invalidate()` wiring after promotions. No configurable import-time embedding cap (uses the method default). No batched inference across multiple tracks/frames.

## Configuration

New fields, all backward-compatible defaults reproducing pre-M15 behavior: `recognition.embedding_cache_refresh_seconds` (2.0), `api.detection_interval_frames` (1 = every frame, unchanged), `database.maximum_embeddings_per_profile` (50).

## Commands executed

- `ruff format`, `ruff check .`, `mypy src tests`: all passed (71 source files).
- Ad hoc, non-persisted interpreter smoke checks (not pytest, not committed as tests):
  - `ActiveProfileEmbeddingCache`: confirmed a new profile added after the first `get()` call is invisible until the refresh interval elapses, then visible; `invalidate()` correctly forces an immediate refresh; a `KnownPersonRecognizer` wired with the cache correctly recognized a known profile.
  - `GeometricFaceTracker.predict_only()`: confirmed correct linear motion extrapolation across two predicted frames and correct re-association with the same track ID once real detection resumed (no spurious new track created).
  - `PipelineWorker` adaptive detection frequency: with `detection_interval_frames=3` over 6 processed frames, the detector was invoked exactly 2 times (frames 0 and 3), verified via `WorkerHealth.frames_detected`.
  - Storage limit: adding a 4th embedding to a profile capped at `max_embeddings=3` was correctly rejected with `ProfileRepositoryError`.
  - `/api/v1/metrics` via `TestClient`: returned correct `active_profile_count` and worker/frame counters; `/api/v1/status` now also reports `frames_detected`.
- Automated `pytest` and the full quality/packaging matrix were **not run**, per the owner's explicit request to defer tests for now.

## Verification status and limitations

No test counts, passing quality gates, or production-readiness claims are made. HERMES's "at least 15 processing FPS" and "recognition confirmation within two seconds" acceptance targets are **not verified** — no real camera or hardware benchmark was available in this session, and no number is fabricated in its place. "No profile creation from one-second appearances" and "low duplicate-profile rate" remain backed by M8's already-verified structural gates and unevaluated threshold defaults respectively, unchanged by this milestone.

## Project-level closing note

This concludes the M4–M15 sequence requested for this session, continuing the M0–M3 work already on `alpha`. Every milestone from M4 onward followed the same pattern: disabled-by-default configuration, mock-first automated-test-free verification via ad hoc smoke checks (explicitly not claimed as a passing automated suite), an ADR and milestone report per change, and one commit pushed to `origin/alpha` per milestone. Several real defects were found and fixed along the way through this session's own smoke testing rather than a test suite (documented in each affected ADR/report): an M6 auto-commit-per-call bug blocking atomic transactions, an AEAD re-keying bug in profile merge, a floating-point boundary bug in M10's switch-margin comparison, a cross-thread SQLite crash and a DELETE-with-JSON-body API defect in M12. HERMES's "Final Objective" (detect/track, assess quality and liveness, identify or manage as candidate, maintain reviewable profiles, select active user, restore settings, learn stable preferences, operate headless, expose clean APIs) has a working implementation of every stage behind explicit, disabled-by-default configuration; what remains before any of it could be called production-complete is exactly what each milestone's report's "Next closure steps" section already lists — most centrally, real automated test coverage (owner-deferred throughout this session) and real-world accuracy/performance evaluation on approved data and hardware, neither of which this environment could honestly provide.
