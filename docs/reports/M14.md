# M14 Implementation Report — Advanced Liveness and Spoof Resistance

- Milestone: M14 — Advanced Liveness
- Date: 2026-08-01
- Status: **Implementation drafted; verification deferred by owner**

## Scope delivered

- `liveness/passive.py`: `HeuristicPassiveLivenessEvaluator` (FFT high-frequency energy ratio + specular-highlight-spread heuristics), disabled by default.
- `liveness/active_challenge.py`: `verify_turn_challenge()`, a deterministic yaw-sequence verifier guarding against pre-turned static replays.
- `liveness/depth.py`: `DepthIRSignal`, an interface-only stub (no real backend).
- `LivenessConfig`, disabled by default.
- Two-point enforcement of "failed liveness cannot create a permanent profile": sticky per-track liveness gating in `CandidateManager` (blocks `READY_FOR_REVIEW`) plus a promotion-time defense-in-depth re-check in `CandidatePromoter` against a persisted `liveness_passed` candidate-metadata flag.
- `PipelineWorker` wiring: evaluates every aligned crop and passes the result into candidate observation when liveness is enabled.

## Explicit exclusions

No trained anti-spoof model (none could be responsibly sourced/vetted/evaluated in this session — see ADR 0002's provenance gate); no real active-challenge frame capture/UI orchestration; no real depth/IR backend. All three remain honestly documented gaps.

## Configuration

`liveness` is disabled by default and bounds `minimum_passive_score`, the high-frequency energy band, `minimum_specular_variance`, `require_active_challenge`, and `active_challenge_min_yaw_delta`.

## Commands executed

- `ruff format`, `ruff check .`, `mypy src tests`: all passed (70 source files).
- Ad hoc, non-persisted interpreter smoke checks (not pytest, not committed as tests):
  - Passive evaluator: exercised against two synthetic images (a smooth gradient and dense random noise) to confirm both configured bounds (spectral-energy band, minimum specular variance) actually gate the result — explicitly **not** claimed as real spoof-detection accuracy evidence, only a code-path self-test.
  - Active challenge: a frontal→left-turn sequence correctly passed a `LEFT` challenge and correctly failed a `RIGHT` challenge; a sequence that started already turned was correctly rejected as `did_not_start_frontal` (defends against a static pre-turned replay).
  - **The critical safety property**, verified against a real temporary M6/M8 database: (a) a candidate whose every sample fails liveness never leaves `COLLECTING` and promotion correctly refuses it as not-ready; (b) a candidate with one failed sample among otherwise-passing samples remains sticky-blocked; (c) a candidate whose samples all pass liveness reaches `READY_FOR_REVIEW` and promotes normally; (d) a simulated bypass — a candidate manually marked `READY_FOR_REVIEW` without the recorded liveness flag — was caught and rejected by the promotion-time defense-in-depth check, with its embeddings deleted.
- Automated `pytest` and the full quality/packaging matrix were **not run**, per the owner's explicit request to defer tests for now.

## Verification status and limitations

No test counts, passing quality gates, or production-readiness claims are made. HERMES/ROADMAP's "static photo attacks are flagged in the standard test set" and "documented rate" requirements are **not** satisfied — there is no standard printed-photo test set available in this environment, and no accuracy rate is claimed. The passive heuristics have unevaluated real-world accuracy and may both under- and over-reject relative to a trained model. Active-challenge frame capture and an accompanying UI/API workflow do not exist; only the verification math does.

## Next closure steps

1. Assemble or obtain an approved, privacy-safe printed-photo/replay test set; measure and document the real rejection rate.
2. Procure and rights-review a trained passive anti-spoof model per ADR 0002, or formally accept the heuristic as the production baseline with that limitation documented.
3. Build real active-challenge orchestration (prompt, capture, verify) once M12's daemon/UI supports a multi-frame interactive flow.
4. Add deterministic unit tests for every scenario exercised ad hoc above.
5. Run the repository quality and packaging matrix.
6. Mark M14 complete only after those results are recorded.
