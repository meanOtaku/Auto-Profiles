# M9 Implementation Report — Settings Abstraction and Initial Platform Adapter

- Milestone: M9 — Settings Abstraction and Initial Platform Adapter
- Date: 2026-08-01
- Status: **Implementation drafted; verification deferred by owner**

## Scope delivered

- `CapabilityStatus`/`AdapterCapabilities` and a `capabilities()` addition to the `SettingsAdapter` protocol; `MockSettingsAdapter` updated accordingly.
- `ApplyResult` extended with `errors`/`rolled_back` (backward-compatible defaults).
- `LinuxSettingsAdapter` (ALSA `amixer` for volume, sysfs backlight for brightness), fully dependency-injected (`CommandRunner`, `BacklightAccessor`) so automated tests never touch real hardware.
- Partial-application rollback: if one of volume/brightness fails after the other succeeded, the adapter rolls the succeeded value back and reports both failures.
- `RateLimitedSettingsAdapter`: rejects rapid repeated applies and records self-applied values (mechanism only; M11 owns attribution/debounce policy).
- `SettingsConfig.backend`/`min_apply_interval_seconds` and `settings/factory.create_settings_adapter()`, wired into the CLI's service path in place of a hardcoded `MockSettingsAdapter`.

## Explicit exclusions

M9 does **not** add active-user selection (M10), preference attribution/debounce (M11), or any additional real OS/DE adapter beyond the one selected platform (Linux/ALSA/sysfs). No desktop-environment-specific daemon integration is included.

## Configuration

`settings.backend` defaults to `mock`. Selecting `linux` opts into the real adapter; `min_apply_interval_seconds` bounds rate limiting.

## Commands executed

- `ruff format` and `ruff check .`: passed.
- `mypy src tests`: passed with no issues in 52 source files.
- Ad hoc, non-persisted interpreter smoke checks (not pytest, not committed as tests):
  - `MockSettingsAdapter` capability reporting and range validation.
  - `RateLimitedSettingsAdapter`: first apply succeeds, immediate second apply is rejected as rate-limited (not recorded), a third apply after the interval elapses succeeds; `recent_self_applications()` correctly reflects only the two successful applies.
  - `LinuxSettingsAdapter` against fakes: both capabilities available; successful dual apply; brightness `PERMISSION_DENIED` when the backlight device exists but is not writable; brightness `UNSUPPORTED` when no backlight device exists; partial failure (brightness write fails after volume succeeds) correctly rolled the volume back and reported `rolled_back=True`; fully unsupported backend (failing command runner + unavailable backlight) correctly reported both capabilities as `UNSUPPORTED` and refused to apply.
  - A real bug was found and fixed during this session's own smoke testing: `_volume_capability()` originally called `shutil.which("amixer")` directly, bypassing the injected `CommandRunner` entirely and making volume-capability detection untestable with fakes (it would report `UNSUPPORTED` even when a fake runner simulated a working `amixer`). Fixed by routing capability detection entirely through the injected command runner.
  - Read-only capability detection against this actual sandboxed environment (no `amixer`, no `/sys/class/backlight` device) correctly reported `UNSUPPORTED` for both settings without any mutation attempt.
  - End-to-end: `face-profile --config config/default.yaml check` runs successfully through the new `create_settings_adapter()` factory.
- Automated `pytest` and the full quality/packaging matrix were **not run**, per the owner's explicit request to defer tests for now.

## Verification status and limitations

No test counts, passing quality gates, or production-readiness claims are made. HERMES's M9 acceptance criteria explicitly require a **manual test on real hardware** verifying safe ranges, rate limits, feedback-loop suppression, and rollback/fail-safe behavior; that manual test has **not** been performed in this environment (no ALSA mixer, no backlight device are present) and is not claimed as passed. Real-adapter code paths beyond capability detection (actual `amixer`/sysfs read and write calls) have only been exercised through fakes, never against real hardware. Feedback-loop *attribution* (deciding whether a later observed change should be saved as a new user preference) is explicitly out of scope; only the recording mechanism it will consume exists.
