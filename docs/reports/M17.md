# M17 Implementation Report — Native Windows Compatibility

- Date: 2026-08-04
- Branch: `alpha`
- Scope: native Windows 10/11 x64 source execution while preserving the Linux path
- Status: implementation and Linux-hosted static/build verification complete; Windows runner and real hardware verification pending

## Delivered

- Cross-platform sensitive-storage boundary:
  - existing POSIX `0700`/`0600` behavior retained;
  - Windows protected NTFS DACL backend using the current process-token user and LocalSystem;
  - inheritable child ACEs on sensitive directories for SQLite WAL/SHM sidecars;
  - symlink/reparse-point rejection and fail-closed verification.
- Deterministic Windows webcam capture through OpenCV DirectShow, plus Windows-specific diagnostics and an honest preflight deferral where no stable device path exists.
- `WindowsSettingsAdapter`:
  - default Core Audio endpoint volume through pycaw;
  - internal-panel brightness through bounded PowerShell/CIM calls to WMI;
  - fail-before-mutation when either capability is unavailable;
  - best-effort volume rollback when a later brightness write fails.
- Platform factory guards that reject Linux settings off Linux and Windows settings off Windows. The mock backend and existing Linux adapter remain available.
- Conditional locked Windows dependencies (`pycaw`, `pywin32`).
- Native operator surface: `run.ps1`, `run-continuous.ps1`, and `scripts/provision-models.ps1`.
- `config/windows-safe.yaml` and `config/windows-full.yaml`.
- Manual, test-free Windows compatibility workflow for Python 3.11 and 3.12.
- Windows runbook and ADR 0021.

## Windows compatibility workflow

`.github/workflows/windows-compatibility.yml` is isolated from the required pytest CI and deliberately does not run pytest or any test runner. On `alpha`, changing only `.github/windows-compatibility-trigger` starts it while `ci.yml` ignores that marker-only push; `workflow_dispatch` is also available once the workflow exists on the default branch. It runs on `windows-latest` for Python 3.11 and 3.12 and performs:

1. frozen dependency installation;
2. source compilation;
3. Ruff lint and changed-file formatting checks;
4. strict mypy;
5. wheel/sdist build;
6. clean-environment wheel installation;
7. hardware-disabled `face-profile check` with `config/windows-safe.yaml`.

Workflow run [30884122482](https://github.com/meanOtaku/Auto-Profiles/actions/runs/30884122482) completed successfully on 2026-08-04. Both the Python 3.11 and 3.12 jobs passed every step above, including clean-wheel installation and the hardware-disabled CLI check. Earlier runs exposed unavailable exact Windows patch versions and Windows-only mypy portability errors; M17 corrected both before this successful run. No test runner was invoked.

## Explicitly deferred to a real Windows host

- the Windows `os.open()` no-follow TOCTOU gap and the first-directory-creation

- transactional settings rollback against real devices;
- `run-continuous.ps1` crash backoff and Ctrl+C behavior;
- Windows Defender Firewall behavior;
- full detection, recognition, enrollment, settings restore, and preference learning on Windows hardware.

## Supported and unsupported claims

Supported now:

- a native Windows source path exists;
- Linux behavior remains represented by the existing Linux adapter and platform factory branch;
- static analysis, lock consistency, and source compilation pass on the development host;
- Windows runner packaging, import, strict static analysis, clean-wheel installation, and the hardware-disabled CLI path pass for Python 3.11 and 3.12.

Not yet supported as claims:

- “complete Windows support”;
- real Windows hardware compatibility;
- NTFS security enforcement observed in practice;
- camera/audio/brightness success rates;
- standalone `.exe`, MSI, or Windows Service support;
- ARM64 Windows support.
