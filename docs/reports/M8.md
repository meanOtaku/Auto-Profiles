# M8 Implementation Report — Candidate Enrollment and Review

- Milestone: M8 — Candidate Enrollment
- Date: 2026-08-01
- Status: **Implementation drafted; verification deferred by owner**

## Scope delivered

- Migration v2: `candidates`, `candidate_embeddings` (AES-256-GCM encrypted, same as profile embeddings), `candidate_name_sequence`.
- `CandidateRepository`: full lifecycle (`COLLECTING → {EXPIRED, REJECTED, READY_FOR_REVIEW} → PROMOTED`), sample storage, immediate embedding deletion on reject/expire/promote (no duplicate or lingering biometric storage).
- `enrollment/qualification.py`: pure `evaluate_candidate_qualification()` covering sample count, observation duration, quality, near-frontal requirement, internal consistency (mixed-identity guard), minimum temporal-variability (spoof/replay heuristic), and duplicate checks against both active profiles and other candidates.
- `enrollment/frontality.py`: self-contained near-frontal pose check.
- `enrollment/manager.py`: `CandidateManager`, per-track candidate association, auto-transition to `READY_FOR_REVIEW`.
- `enrollment/promotion.py`: `CandidatePromoter`, atomic/auditable/idempotent promotion with a promotion-time duplicate re-check.
- `EnrollmentConfig`, disabled by default, with `automatic_promotion` **unconditionally rejected** by validation until M12/M14 production gates exist.
- CLI `candidate list|show|approve|reject`.

## Prerequisite correction to M6

While implementing atomic promotion, this session found that M6's repository write methods each committed their own transaction, making it impossible to compose multiple writes (profile create + N embedding transfers + candidate state change + audit event) into one atomic unit. This is a real defect in still-unverified M6 code, not a hypothetical concern: `merge()` already avoided it by design, but `create()`, `update()`, `add_embedding()`, and others did not. Fixed by removing per-call commits and adding explicit `ProfileDatabase.commit()`/`.rollback()`; `merge()` and `import_profile()` remain self-committing since each is its own atomic unit. The M6 `profile` CLI commands were updated accordingly and re-verified (see Commands Executed).

## Explicit exclusions

M8 does **not** add trained liveness/anti-spoof (M14), the REST `/api/v1/candidates/...` surface (M12), active-user selection (M10), or real settings adapters (M9). The temporal-variability check is a documented statistical heuristic over the candidate's own samples, not a trained model.

## Configuration

`enrollment` is disabled by default. `automatic_promotion=true` is rejected by a pydantic validator regardless of the caller's intent, verified in this session — this directly implements TESTING.md's required scenario 14.

## Commands executed

- `ruff format` and `ruff check src tests`: passed.
- `mypy src tests`: passed with no issues in 49 source files.
- Ad hoc, non-persisted interpreter smoke checks (not pytest, not committed as tests), covering every M8 acceptance criterion:
  - One-frame observation: candidate stays `COLLECTING` after a single sample (`minimum_samples=3` not met) — never reaches `READY_FOR_REVIEW`, never promotable.
  - Two simultaneous unknown people: distinct track IDs produced distinct candidate IDs and temporary names.
  - Full qualification → promotion: 4 samples over >2 observed seconds with realistic embedding jitter reached `READY_FOR_REVIEW`; promotion created exactly one profile with all embeddings transferred, deleted the candidate-side embedding copies, recorded a `ProfileCreated` audit event linking `profile_id` and `candidate_id`, and a repeated `promote()` call returned the identical profile without further writes (idempotency).
  - Duplicate-profile race: a candidate that qualified before any matching active profile existed was correctly rejected — and its embeddings deleted — when `promote()` re-checked after a matching profile appeared in the interim; no duplicate profile was created.
  - Poorly observed candidate expiry: a single-sample candidate was expired by `expire_stale()` after its window passed, its embeddings deleted, and no profile was ever created.
  - `automatic_promotion=True` was rejected by configuration validation with a clear message.
  - M6 regression check: create/update/add_embedding/settings-upsert/event-record with explicit caller-side commits, and merge/import_profile's own internal commit, all still behave correctly after the auto-commit removal.
  - CLI end-to-end: `candidate list/show/approve/reject` and `profile list` against a real temporary SQLite database, including a full seed → list → show → approve → verify-profile-created flow.
- Automated `pytest` and the full quality/packaging matrix were **not run**, per the owner's explicit request to defer tests for now.

## Verification status and limitations

No test counts, passing quality gates, or production-readiness claims are made. The two scenarios noted in ADR 0013 as deferred remain deferred: concurrent promotion attempts (TESTING.md scenario 10) rely on SQLite's own serialization/`busy_timeout` without dedicated testing, and printed-photo/replay resistance rests on mandatory manual approval plus a statistical heuristic, not a trained model (M14's explicit job). `CandidateManager`'s active-profile and other-candidate embedding scans are the same documented O(n) decrypt-per-call performance limitation carried from M7, deferred to M15. `purge_terminal()` for old expired/rejected candidate rows exists on the repository but is not yet wired to any scheduled caller (no worker exists before M12).
