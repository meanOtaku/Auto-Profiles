# M11 Implementation Report — Last-Used Preference Persistence

- Milestone: M11 — Last-Used Settings
- Date: 2026-08-01
- Status: **Implementation drafted; verification deferred by owner**

## Scope delivered

- `settings/preference_learning.py`: `PreferenceLearner`, implementing HERMES.md's four attribution rules (single active profile, minimum active duration, debounce stability, self-application suppression) as sequential gates, plus redundant-save suppression.
- `settings/last_used_service.py`: `LastUsedPreferenceService`, the read-observe-save orchestration tying the settings adapter, learner, and M6 persistence (settings upsert + durable `SettingsChanged` event) together in one committed transaction.
- `PreferenceLearningConfig`, disabled by default, and `settings/factory.create_last_used_preference_service()`.

## Explicit exclusions

M11 does **not** poll settings on a timer itself (M12's daemon worker loop will call `observe()` periodically), apply settings (M9), or select the active user (M10).

**Update (2026-08-02, see `docs/reports/M16.md`):** M12 did wire `observe()` into the worker's per-frame loop, but nothing was ever added to fill the "apply settings" exclusion above -- a recognized returning user's saved volume/brightness was never restored, only ever saved. M16 adds `settings/active_profile_applier.py` (constructed automatically whenever the profile database is enabled, since HERMES.md treats restore-on-recognition as a mandatory pipeline step) and confirms, with a real integration test, that it composes correctly with this module's existing self-applied-echo suppression rather than requiring any change to it.

## Configuration

`preference_learning` is disabled by default and bounds `debounce_seconds`, `min_active_duration_seconds`, and `self_application_tolerance_seconds`.

## Commands executed

- `ruff format` and `ruff check .`: passed.
- `mypy src tests`: passed with no issues in 58 source files.
- Ad hoc, non-persisted interpreter smoke checks (not pytest, not committed as tests), covering every documented attribution rule and TESTING.md §8-relevant scenario:
  1. No active profile: never saved.
  2. Self-applied value observed again: not treated as new user input.
  3. User changes a value and it stabilizes: not saved on first observation or mid-debounce, saved once stable past the debounce period.
  4. Re-observing an already-saved unchanged value: not redundantly re-saved.
  5. Rapid slider movement (four different values in quick succession): never accumulates enough stable time to save.
  6. Profile switch: a value stable under the previous active profile is not attributed to the newly active profile without its own fresh debounce wait; once it does stabilize, it is correctly saved to the new profile.
  - End-to-end `LastUsedPreferenceService` against a real temporary M6 SQLite database: a self-applied value via `RateLimitedSettingsAdapter.apply()` was correctly ignored; a directly-mutated ("externally changed") mock adapter value was correctly debounced then persisted to the active profile's `profile_settings` row, with a durable `SettingsChanged` audit event recorded.
- Automated `pytest` and the full quality/packaging matrix were **not run**, per the owner's explicit request to defer tests for now.

## Verification status and limitations

No test counts, passing quality gates, or production-readiness claims are made. `LastUsedPreferenceService.observe()` is called on demand by a caller; no scheduled polling loop exists yet (M12's job). Debounce/minimum-active-duration defaults are unevaluated starting points. The module has not been exercised against the real `LinuxSettingsAdapter` (M9) reading actual host state — only `MockSettingsAdapter` was used, consistent with this environment having no real audio/backlight device to observe.
