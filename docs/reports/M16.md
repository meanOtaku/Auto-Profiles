- Date: 2026-08-02
- Status: **Implementation drafted and locally verified with real, independently

## The gap this report closes

HERMES.md's high-level pipeline (`## High-Level Pipeline`) lists, in order:
"Select active user" -> **"Load and apply active profile settings"** -> "Emit
events and persist state". Auditing the real implementation (not the milestone
reports' claims) found this middle step did not exist anywhere:

- `presence/active_user.py` (M10) only *selects* an active profile; its own
  module docstring says so explicitly.
- `settings/last_used_service.py` (M11) only *observes current settings and
  saves stable changes*; its own module docstring calls it "the M11
  read-observe-save cycle" and explicitly says "This module never applies
  settings (M9)".
- `docs/reports/M10.md` and `docs/reports/M11.md` both explicitly list
  "does not apply settings" under "Explicit exclusions" for their own milestone,
  and neither claims the other does it.
- `api/worker.py`'s per-frame loop called `active_user_selector.update(...)` and
  then only `preference_service.observe(...)` (the save side) -- nothing ever
  read `ProfileDatabase.settings.get(profile_id)` and called
  `adapter.apply(...)` on a recognized activation.

So a recognized returning user's previously-saved volume/brightness was never
restored; the owner's request ("carefully verify whether a recognized
active-profile transition actually loads and applies `ProfileDatabase.settings`;
do not assume milestone claims are correct") was correct to be suspicious, and the
suspicion was confirmed by reading the code, not assumed.

## Scope delivered

### 1. `ActiveProfileSettingsApplier` (`settings/active_profile_applier.py`)

The missing M9/M10 bridge: on a stable transition to a new active profile, loads
`ProfileDatabase.settings.get(profile_id)` and applies it through the existing
rate-limited adapter exactly once per activation. Repeated frames for the same
still-active profile never re-touch hardware; a profile with no saved settings
causes no mutation; a failed or rate-limited apply is recorded as a distinct
`SettingsApplyFailed` durable event (never `SettingsApplied`) and is not retried
every subsequent frame, so a persistently failing adapter cannot be hammered
either. Wired into `api/worker.py`'s per-frame loop (right after the M10 decision,
before M11's `observe()`, matching HERMES's documented pipeline order) and into
`api/app.py`/`settings/factory.py` (`create_active_profile_settings_applier()`),
constructed automatically whenever a profile database exists -- restoring saved
settings is a mandatory pipeline step per HERMES.md, not a separate opt-in flag.

Strict TDD was used: `tests/unit/test_active_profile_settings_applier.py` (8
tests) was written first and confirmed to fail for the right reason (missing
module) before any implementation existed, covering the 5 required scenarios:
stable transition applies stored settings exactly once; repeated frames for the
same active profile do not reapply; switching profiles applies the new profile's
settings; a profile with no saved settings causes no mutation; a failed and,
separately, a rate-limited apply are both audited via a durable event and never
recorded as success.
`tests/unit/test_settings_apply_and_learn_integration.py` proves the 6th
scenario end-to-end against a real temporary SQLite `ProfileDatabase`: a
self-applied restore is correctly suppressed by M11's existing
`self_applied_echo` attribution rule (no code change needed there -- the
existing feedback-loop suppression already composes correctly with the new
applier), while a later, genuinely different, stable user change still debounces
and persists to the active profile.
`tests/unit/test_pipeline_worker_settings_apply.py` and
`tests/unit/test_app_settings_applier_wiring.py` prove the 7th scenario: the
worker calls `settings_applier.sync(active=...)` every processed frame when an
active-user selector is configured (and never when one is not), and
`create_app()` wires a real `ActiveProfileSettingsApplier` into the worker
whenever the profile database is enabled (`None` when it is not).

### 2. `OnnxEmbeddingGenerator` preprocessing made configurable (`vision/embedding.py`, `config.py`)

While researching a real embedding model to pin (see below), auditing
`OnnxEmbeddingGenerator` found its preprocessing (`mean=(127.5,127.5,127.5)`,
`scalefactor=1/128`) was a hardcoded class constant calibrated for one specific
model family (InsightFace/ArcFace-style), not configurable. OpenCV Zoo's SFace
model requires materially different preprocessing (`mean=(0,0,0)`,
`scalefactor=1`, confirmed directly against OpenCV's own C++ source -- see
`docs/MODELS.md`). Pinning SFace against the unmodified adapter would have fed it
badly-scaled input and silently produced meaningless embeddings while appearing
to work (correct shape, no exception) -- exactly the "pretending full recognition
works" failure mode the owner's instructions warned against.

Fixed by adding `EmbeddingConfig.input_mean`/`input_scale` (defaulting to the
original ArcFace-style values for backward compatibility -- no existing config or
test depended on the old hardcoded constants, confirmed by search) and threading
them through `OnnxEmbeddingGenerator.__init__()` and `create_embedding_generator()`.
`tests/unit/test_embedding_onnx_preprocessing.py` (3 tests, TDD: confirmed to fail
for the right reason -- `unexpected keyword argument 'input_mean'` -- before the
fix) proves the generator actually applies the *configured* mean/scale rather
than a fixed constant, using a capturing fake backend and a constant-valued test
image so the assertion isolates preprocessing correctness from resize/channel-order
effects.

### 3. Real, independently-verified SFace model pinned (`docs/MODELS.md`)

Per the owner's explicit instruction not to fabricate provenance, both the YuNet
detector (already pinned in `config/jetson-webcam.yaml`) and a new SFace embedding
model's SHA-256 were re-derived directly from the live `opencv/opencv_zoo`
repository in this session (not copied from memory): the real 38,696,353-byte
file was downloaded, hashed, and confirmed to match the upstream Git LFS pointer's
own recorded `oid`; loaded for real with `cv2.dnn.readNetFromONNX` and run through
a forward pass (confirmed `(1, 128)` output); and run through the *fixed*
`OnnxEmbeddingGenerator` end-to-end producing a finite, unit-norm 128-d vector.
See `docs/MODELS.md` for the full provenance record, exact hashes, and the
step-by-step verification method (so it can be independently re-checked, not just
trusted).

A real, pre-existing documentation/tooling gap was also found and is recorded
(not silently fixed elsewhere): the existing `Webcam_demo.sh` and
`docs/RUNNING_ON_UBUNTU.md` section 6 use
`https://github.com/opencv/opencv_zoo/raw/main/...` to fetch the YuNet model; that
URL resolves to a 131-byte Git LFS *pointer* file, not the real 232,589-byte
model, for this repository today (confirmed directly). The existing SHA-256 check
in both places would correctly fail closed rather than silently accepting the
wrong file, so this is not a security gap, but the download step as documented
does not actually work. `scripts/provision-models.sh` (new, this report) uses
`media.githubusercontent.com` instead, confirmed working for both models.

While running this report's own required shell-syntax check (`bash -n`) against
every shell script in the repository, `Webcam_demo.sh` was additionally found to
not even parse (`bash -n`: "line 92: syntax error: unexpected end of file" -- its
final `if [[ ! -f "$OUTPUT_FILE" ]]; then` block is truncated, missing its body
and `fi`). This predates this session (`git log -1 -- Webcam_demo.sh`: commit
`d6e654b`, "Add webcam demo script for face detection") and this session never
edited the file. Fixing `Webcam_demo.sh` (both this syntax error and the LFS-URL
issue above) and `docs/RUNNING_ON_UBUNTU.md` section 6 was left out of scope for
this report, per the owner's instruction not to touch unrelated files; flagged
here so neither is silently rediscovered later.

### 4. `config/jetson-full.yaml`

The requested full opt-in path: USB webcam, integrity-pinned YuNet, tracking,
quality/alignment, the integrity-pinned SFace embedding model (with the correct,
independently-confirmed `input_mean`/`input_scale`), an encrypted profile
database, recognition, safety-gated automatic enrollment (`automatic_promotion:
true` plus explicit consent acknowledgement and enabled passive liveness),
active-user selection, preference learning (both the new load-and-apply
restore and the existing debounced save-back), the loopback-only API (no
`auth_token`, `bind_host: 127.0.0.1` -- never edit this tracked file to expose it
further), the UI, and the real Linux settings backend. Passive liveness is now
enabled as a mandatory automatic-promotion gate, but its classical heuristic
accuracy remains unevaluated (`docs/reports/M14.md`) and is not claimed as
production-grade anti-spoofing.

Verified for real (not just "should load"): `load_config()` accepts the file with
no validation errors, and `create_app()` (with a temporary database path, so
`data/local.yaml`/`data/` were never touched) built a working `PipelineWorker`
with a real `KnownPersonRecognizer`, `CandidateManager`, and
`ActiveProfileSettingsApplier`, using the real downloaded and verified model
files.

### 5. `scripts/provision-models.sh`

Idempotent download+verify for both pinned models: skips (no re-download) a file
already present with the correct hash; refuses to overwrite a file present with
an *incorrect* hash rather than silently replacing it; deletes a partial/corrupt
download and fails closed on any hash mismatch or Git-LFS-pointer false-download.
Actually run three times against a real scratch directory in this session:
fresh download of both real files (verified), a no-op idempotent second run, and
a deliberately corrupted existing file correctly refused rather than silently
overwritten.

### 6. `preflight` CLI command (`face-profile --config ... preflight`, `diagnostics/preflight.py`)

Implemented as a `face-profile` subcommand (not a separate script) since it
mirrors the CLI's existing `check`/`detect` structured-JSON-event pattern and
gains that pattern's own test coverage conventions. Every check is read-only:
model checks only hash bytes (never load them into an inference engine), the
camera check only `stat`s and permission-checks an (injectable, for testing) device
path (never opens a `VideoCapture`), and the settings check calls the real
`LinuxSettingsAdapter.capabilities()` -- itself already documented as read-only in
`settings/linux.py` (`SysfsBacklightAccessor.is_writable`'s docstring explicitly
says "it never writes to the device"). TDD: `tests/unit/test_preflight.py` (13
tests) and two `tests/integration/test_cli.py` wiring tests were written and
confirmed to fail for the right reason before the module/CLI branch existed.

Actually run against the real `config/jetson-full.yaml` with the real downloaded
models in this (non-Jetson) sandbox:

```
preflight check: detection_model=pass (verified 232589 bytes at models/face_detection_yunet_2023mar.onnx)
preflight check: embedding_model=pass (verified 38696353 bytes at models/face_recognition_sface_2021dec.onnx)
preflight check: camera_device=fail (/dev/video0 does not exist)
preflight check: settings_capabilities=fail (amixer volume control not available: volume=unsupported, brightness=unsupported)
preflight checks failed
exit code: 3
```

This is the expected, honest result on hardware without a webcam or ALSA mixer --
exactly the fail-closed behavior a preflight tool should have, and exactly what a
real Jetson run is expected to differ on (see `docs/RUNNING_ON_JETSON.md` section
9).

## Configuration

- `EmbeddingConfig.input_mean` (default `127.5`) / `input_scale` (default
  `1.0/128.0`): new, backward-compatible fields; `mock` backend rejects any
  non-default value, matching the existing pattern for `dimension`/`input_width`/

  "load and apply active profile settings" as a mandatory pipeline step, not an
  optional one (unlike `preference_learning.enabled`, which still separately
  gates the *save-back* side).
